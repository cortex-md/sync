# Self-hosting Cortex Sync

This guide covers two paths:

1. [Render + Neon + R2 + Resend](#render--neon--r2--resend): the reference deployment, defined
   by [`render.yaml`](../render.yaml) and [`.env.example`](../.env.example).
2. [Generic Docker](#generic-docker): the same image on your own machine, VPS or cluster.

Every variable mentioned here is described in [configuration.md](configuration.md).

## Render + Neon + R2 + Resend

One Render web service (Docker runtime, `CORTEX_DEPLOYMENT=single`) runs the server, Neon hosts
PostgreSQL, Cloudflare R2 stores the encrypted snapshots and Resend delivers email.

### 1. Create R2 storage

Create one private R2 bucket for snapshots, then create an R2 API token with Object Read & Write
permission scoped to that bucket. Note the S3 API endpoint from Cloudflare:

```text
https://<account-id>.r2.cloudflarestorage.com
```

The server never creates remote buckets, so the bucket must exist before the first deploy. The
Blueprint names it `cortex-snapshots`; change `CORTEX_STORAGE_BUCKET` if yours differs.

### 2. Create the Neon database

Create a Neon project in the AWS region closest to the Render region. `render.yaml` uses
`virginia`, which pairs with Neon's `us-east-1`; every request makes several database round trips,
so keep both in the same region.

Copy the **direct** connection string, the one whose host does not contain `-pooler`, and keep
`sslmode=require`:

```env
CORTEX_DATABASE_URL=postgresql://<user>:<password>@<endpoint>.<region>.aws.neon.tech/<db>?sslmode=require
```

Do not use the pooled endpoint. Migrations hold a session-level advisory lock, which a
transaction-mode pooler does not preserve, and the server already keeps its own small pool
(5 connections in `single` mode).

Neon provides point-in-time restore, so no separate backup job is needed for this setup.

### 3. Set up Resend

Render's free plan blocks outbound SMTP ports, so use the `resend` mail driver. In Resend, verify
the domain you send from and create an API key with sending access. `CORTEX_MAIL_FROM` must use the
verified domain, for example `Cortex <no-reply@example.com>`.

Each outbox row is sent with its own `Idempotency-Key`, so a retried request is not delivered
twice. If you do not want email at all, set `CORTEX_MAIL_DRIVER=none`: email verification,
password reset and email-addressed invites are then off, and invites only work through their link.

### 4. Create the Render service

In Render, create a new Blueprint and point it at your fork of this repository. Render reads
`render.yaml` and creates the `cortex-sync` web service. Fill in the values marked `sync: false`
when prompted:

| Variable | Value |
|----------|-------|
| `CORTEX_SERVER_PUBLIC_URL` | `https://<your-service>.onrender.com` or your custom domain |
| `CORTEX_DATABASE_URL` | Neon direct connection string |
| `CORTEX_STORAGE_ENDPOINT` | `https://<account-id>.r2.cloudflarestorage.com` |
| `CORTEX_STORAGE_ACCESS_KEY` / `CORTEX_STORAGE_SECRET_KEY` | R2 token credentials |
| `CORTEX_MAIL_RESEND_API_KEY` | Resend API key |
| Stripe and Discord values | Leave empty unless you enable them |

`CORTEX_AUTH_ACCESS_TOKEN_SECRET` is generated by Render. Review the values the Blueprint sets
explicitly before the first deploy, because they describe Cortex Cloud:

- `CORTEX_MAIL_FROM` and `CORTEX_CORS_ALLOWED_ORIGINS` point at `cortex-md.tech`; change them to
  your domain (desktop and mobile clients do not need CORS).
- `CORTEX_AUTH_REGISTRATION_MODE=open`; use `first-user` for a private server.
- `CORTEX_TENANCY_MODE=multi` with a `1GiB` default vault quota and per-account caps; use `single`
  if you do not need quotas.
- `CORTEX_FEATURES=collab,avatars,guests,public_links`; drop what you do not want.
- `CORTEX_PROXY=render` and `CORTEX_PROTECTION=standard`.

The service listens on port `10000` (`CORTEX_SERVER_PORT`), uses `/health` as its health check and
redeploys automatically once the commit's checks pass (`autoDeployTrigger: checksPass`).
Migrations run on boot because the deployment mode is `single`.

### 5. Verify the client IP setting

Rate limits and the login lockout key on the client IP, so confirm that `CORTEX_PROXY=render`
resolves your real address after the first deploy. Failed requests are logged with `client_ip`;
request a route that does not exist and compare it with your public address:

```bash
curl -s https://<your-service>.onrender.com/does-not-exist
curl -s https://api.ipify.org
```

The `request failed` log line in the Render dashboard should show the address returned by the
second command. If it shows a private Render address, the proxy mode is wrong. If the log contains
`requests carry X-Forwarded-For but CORTEX_PROXY=none`, the variable is missing.

Also check the `configuration` line logged on boot and any warnings above it.

### 6. Know the free plan limits

- The service sleeps after about 15 minutes without traffic. The next request waits for a cold
  start of roughly a minute, and background jobs (cleanup, mail sweeps) only run while it is awake.
- The free plan runs exactly one instance, so it cannot scale horizontally. Keep
  `CORTEX_DEPLOYMENT=single`.
- Outbound SMTP ports are blocked; use `resend`.

A paid plan removes the sleep. To run several instances, switch to `CORTEX_DEPLOYMENT=cluster` and
run `cortex-sync migrate up` before each rollout (see
[Multiple replicas behind Cloudflare](#multiple-replicas-behind-cloudflare)).

### 7. Configure Cortex Desktop

Open Settings > Self-hosted sync in Cortex and set the Sync URL to your public URL, for example:

```text
https://<your-service>.onrender.com
```

Then sign in or register against that server and link the vault.

## Generic Docker

GitHub Actions publishes multi-arch images to `ghcr.io/cortex-md/sync` from `main`, commit SHA
tags (`sha-<commit>`) and version tags (`0.1.0`, `0.1`, `latest`). Deploy an explicit version.

The image is distroless (`gcr.io/distroless/static-debian12:nonroot`): there is no shell and no
built-in `HEALTHCHECK`. Configure probes in your orchestrator or load balancer instead:

- `/health` for liveness (the process is up).
- `/ready` for readiness (database and storage reachable, `503` while draining).

The binary has a `migrate` subcommand: `cortex-sync migrate up`, `migrate down N` and
`migrate version`.

You need PostgreSQL 16 and S3-compatible storage (R2, S3, MinIO, SeaweedFS). With
`CORTEX_STORAGE_BACKEND=s3` the bucket must exist beforehand; an `http://` endpoint disables TLS.

### Home or private network

One process on a trusted network, no reverse proxy, no email and no quotas:

```env
CORTEX_SERVER_ENV=production
CORTEX_SERVER_PUBLIC_URL=http://192.168.1.10:8080

CORTEX_DEPLOYMENT=single
CORTEX_PROXY=none
CORTEX_PROTECTION=off
CORTEX_TENANCY_MODE=single
CORTEX_MAIL_DRIVER=none
CORTEX_AUTH_REGISTRATION_MODE=first-user

CORTEX_DATABASE_URL=postgres://cortex:<password>@postgres:5432/cortex_sync?sslmode=disable
CORTEX_AUTH_ACCESS_TOKEN_SECRET=<openssl rand -hex 32>

CORTEX_STORAGE_BACKEND=s3
CORTEX_STORAGE_ENDPOINT=http://minio:9000
CORTEX_STORAGE_ACCESS_KEY=<key>
CORTEX_STORAGE_SECRET_KEY=<secret>
CORTEX_STORAGE_BUCKET=cortex-snapshots
```

```bash
docker run -d --name cortex-sync --restart unless-stopped \
  --env-file .env -p 8080:8080 ghcr.io/cortex-md/sync:0.1.0
```

Migrations run on boot. With `CORTEX_MAIL_DRIVER=none`, share invites by sending the
`invite_url` returned when you create them. `CORTEX_PROTECTION=off` disables rate limits and
connection caps; switch to `standard` if the server is reachable from the internet.

### Multiple replicas behind Cloudflare

Several replicas behind a load balancer, with Cloudflare in front and SMTP for email:

```env
CORTEX_SERVER_ENV=production
CORTEX_SERVER_PUBLIC_URL=https://sync.example.com
CORTEX_SERVER_DRAIN_DELAY=5s

CORTEX_DEPLOYMENT=cluster
CORTEX_PROXY=cloudflare
CORTEX_PROTECTION=standard
CORTEX_AUTH_REGISTRATION_MODE=open

CORTEX_DATABASE_URL=postgres://cortex:<password>@db.internal:5432/cortex_sync?sslmode=require
CORTEX_AUTH_ACCESS_TOKEN_SECRET=<openssl rand -hex 32, shared by every replica>

CORTEX_MAIL_DRIVER=smtp
CORTEX_MAIL_HOST=smtp.example.com
CORTEX_MAIL_PORT=587
CORTEX_MAIL_USERNAME=<user>
CORTEX_MAIL_PASSWORD=<password>
CORTEX_MAIL_FROM=Cortex <no-reply@example.com>

CORTEX_STORAGE_BACKEND=r2
CORTEX_STORAGE_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
CORTEX_STORAGE_ACCESS_KEY=<key>
CORTEX_STORAGE_SECRET_KEY=<secret>
CORTEX_STORAGE_BUCKET=cortex-snapshots
```

In `cluster` mode the replicas coordinate through PostgreSQL `LISTEN/NOTIFY`, so no sticky
sessions are needed, and migrations do not run on boot. Roll out a new version like this:

```bash
docker run --rm --env-file .env ghcr.io/cortex-md/sync:0.2.0 migrate up
```

Then replace the replicas one at a time, waiting for each new one to report `/ready` before
stopping the next old one. `CORTEX_SERVER_DRAIN_DELAY` keeps `/ready` at `503` for that long before
SSE and collab streams are closed, so the load balancer stops routing first.

Things to check:

- `CORTEX_PROXY=cloudflare` trusts `CF-Connecting-IP`. Only use it when the origin is reachable
  exclusively through Cloudflare (a tunnel, or a firewall that allows only Cloudflare addresses).
  Behind a plain reverse proxy, use `hops:N` with the number of proxies instead.
- Each replica opens up to 10 database connections by default (`CORTEX_DATABASE_MAX_CONNS`) plus
  one `LISTEN` connection. Size `max_connections` on PostgreSQL accordingly, and use a direct
  connection rather than a transaction-mode pooler.
- Concurrency and stream caps from `CORTEX_PROTECTION` are per replica.

### Backups

For self-managed PostgreSQL, run `pg_dump -Fc` before upgrades and on a schedule, copy the dumps
off the host, and test a restore with `pg_restore` now and then. Snapshot blobs live in object
storage, but the database holds users, devices, vault membership, keys, sync events and the object
keys, so database backups are required for disaster recovery.

## Maintenance

- Rotate `CORTEX_AUTH_ACCESS_TOKEN_SECRET` only with a planned sign-out window; existing access
  tokens become invalid.
- Rotate R2 or S3 keys by adding a new key in the storage provider, updating the environment,
  deploying, then revoking the old key.
- Keep `CORTEX_AUTH_REGISTRATION_MODE=first-user` for private servers after the first account is
  created, or switch it to `closed` when all expected users are invited.
- Keep `CORTEX_CORS_ALLOW_CREDENTIALS=false` unless you need cookie credentials. Bearer-token
  desktop clients do not require browser credential mode.
- Leave `metrics` out of `CORTEX_FEATURES` unless `/metrics` is exposed only on a private network
  or behind your own authentication.
- Subscriptions stay disabled (`CORTEX_SUBSCRIPTION_ENABLED=false`) for normal self-hosting. When
  enabled, production startup requires the Stripe secret key, price ID and webhook secret, and
  sync-mutating endpoints return `402` until the user has an active entitlement.
- `CORTEX_DEVOPS_DISCORD_WEBHOOK_URL` sends account, device reuse, checkout and subscription
  events to Discord. Messages include user IDs, email addresses and billing metadata, so use a
  private channel and rotate the webhook if it is exposed. Delivery failures are logged and never
  block user-facing flows.
- Check the `configuration` log line and warnings after every upgrade.
